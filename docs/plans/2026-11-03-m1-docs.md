# M1 Documentation Package Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Subagents never commit, push or change GitHub; the orchestrator session commits, opens PRs and closes Issues.

**Goal:** Make DDF's `docs/`, `prompts/`, `schemas/` and `templates/` the single orchestration canon, so an interactive LLM session can run a DDF task by `docs/orchestrator/manual-mode.md` alone.

**Architecture:** Documentation is derived section by section from the V1 spec; nothing new is decided here. The spec stays the design record; docs are the operational canon and link back to spec sections instead of restating rationale. One PR per task group keeps reviews small.

**Tech Stack:** Markdown, JSON Schema (draft 2020-12), YAML examples, GitHub issue forms.

**Spec:** `docs/specs/2026-11-03-ddf-v1-design.md`

## Global Constraints

- English only. Public repository: no IPs, hostnames, locations, hardware, tokens, private repository names, personal logins other than as `<owner>` placeholders.
- Do not mention or explain the internal meaning of the project name.
- No model names outside examples clearly marked "example"; roles name tiers (`frontier|deep|standard|routine|fast`), never models.
- Each doc ≤ 250 lines; link to spec sections (`../specs/2026-11-03-ddf-v1-design.md#…`) instead of copying rationale; do not duplicate prompt text into docs.
- Every doc starts with a one-line purpose and a `Status:` line (`normative` | `implemented in Mx` | `historical`).
- Values copied from the spec verbatim: bounds table §5.3, risk table §6.2, forbidden defaults §6.5, gate conditions §6.6, App permissions §8.2.
- Branch roles stay as in `AGENTS.md`; agent branches `slave/<feature>` target `master`.

## Review Focus

1. A doc that contradicts the spec (a bound, a path, a permission): the docs-consistency check in Task 6 greps the copied tables against the spec.
2. `manual-mode.md` that silently lets the session merge: it must state the human merges in manual mode, in its first screen.
3. A prompt that tells reviewers to run commands: reviewer prompts must forbid command execution (spec §7.1).
4. A schema that accepts a result without a verdict or with unknown fields: schemas set `required` and `additionalProperties: false`.
5. Broken relative links after files move: the link check in Task 6 resolves every relative link.

**Interfaces:**
- Consumes: anchors from Task 2.
- Produces: result shapes the M2 core and M3 adapters implement:

### Task 4: Orchestrator canon

**Files:**
- Create: `docs/orchestrator/manual-mode.md`, `docs/orchestrator/supervisor-mode.md`, `docs/orchestrator/handoff.md`
- Create: `templates/handoff-comment.md`

**Interfaces:**
- Consumes: `docs/concepts/*` anchors, `prompts/*`, `schemas/*`.

- [ ] **Step 1:** `manual-mode.md`, first screen: "In manual mode a human merges. The session never merges, force-pushes or edits forbidden paths." Then the procedure mapped to lifecycle states: intake check (allow-listed author, labels) → Planner pass (session itself or a subagent with `prompts/planner.md`, output validated against the schema) → Executor subagents (exact file list + done criteria + verify commands per brief; at most 3 in parallel; disjoint files) → local verify → one commit and one push per revision by the session → PR with body from `templates/project/.ddf/change-template.md` → wait for required checks on the head → reviewers as **separate sessions** (not subagents) on the same head, set chosen by risk class → correction batches ≤ 3 with full re-review → hand to human for merge → post-merge cleanup (delete worktree and branch only after the PR is MERGED). Include the bounds table (§5.3) and the "what goes to the owner" list (hard stops §6.4, refusals that map to `needs-owner`).
- [ ] **Step 2:** `supervisor-mode.md`: the session uses only `ddf` CLI commands (`status`, `show`, `ask`, `answer`, `pause`, `resume`); never writes code; how to unblock each `needs-owner` category; mark `Status: implemented in M4`.
- [ ] **Step 3:** `handoff.md` + `templates/handoff-comment.md`: state lives in Issues/PRs and `ddf status`; a handoff is one comment on the tracking Issue with sections `Done`, `In flight (PR, head SHA, state)`, `Waiting on owner`, `Next`, `Worktrees`. No dated local handoff files.
- [ ] **Step 4:** Orchestrator commits `docs(ddf): orchestrator canon`.
