# M0 facts

Evidence for the open facts in the V1 spec (`docs/specs/2026-11-03-ddf-v1-design.md` §16), so the M2–M4 plans are written against known behaviour.

Status: recorded 2026-11-04. All six facts answered with their confidence; open items (rate-limit error shapes, App approvals, provision-hook rerun, host reboot) name the probe that closes them in M3/M4/M5.

Confidence levels: `verified` = observed directly in this research; `documented` = stated by official documentation, not yet observed; `unverified` = inferred from indirect or third-party sources, needs the named M4 probe.

## GitHub

### App approvals and required reviews (§16 item 1)

**Answer:** Probably yes, with an open condition. No official page states directly that an APPROVE review by a GitHub App installation counts toward a ruleset's or branch protection's required approvals. Indirect official evidence says it can: GitHub added an organisation setting "Allow GitHub Actions reviews to count towards required approval", and `github-actions[bot]` is itself a GitHub App identity, so App reviews are at least eligible to count. Official docs require approvals to come from reviewers "with write or admin permissions" and do not say how that maps onto App permissions. Open condition: whether an App with `contents: read` + `pull_requests: write` (the spec's reviewer Apps) counts as having write access, or whether it needs `contents: write`.

**Evidence:**
- Branch protection: approvals must come from "people with write permissions in the repository"; Apps and bots are not mentioned. https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- Approving with required reviews: approvals that count come from people with write or admin permissions; Copilot reviews explicitly do not count; Apps in general are not mentioned. https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews
- Changelog (2022-01-13): Actions approvals can satisfy required approvals; the setting that allows this is on by default and an organisation admin can turn it off. https://github.blog/changelog/2022-01-13-github-actions-prevent-github-actions-from-approving-pull-requests
- Community discussion, no GitHub staff answer, answers conflict: one reply says dedicated App and machine-user approvals count, another says only real user approvals count. https://github.com/orgs/community/discussions/181487
- A public third-party automation uses a GitHub App token for approvals that satisfy its merge rules (including last-push approval). Indicative only. https://github.com/petry-projects/.github/pull/141

**Confidence:** unverified.

**Consequence for spec:** None yet. D6 (three Apps) stays; the machine-user fallback stays documented. If the M4 probe shows reviewer Apps need `contents: write` for their approval to count, §8.2 must either grant `contents: write` to the reviewer Apps (weakening the read-only reviewer boundary; the token broker could still mint reviewer tokens narrowed to `contents: read` for everything except the review call) or switch to machine users. Independent of the outcome, the DDF gate (§6.6) does not depend on native approvals; native reviews only matter for the recommended ruleset (§8.6).

**M4 probe:** `app-approval-counts` — on a test repository with a ruleset requiring one approval and no bypass actors: the `worker` App opens a PR; `review-correctness` (`contents: read`, `pull_requests: write`) submits APPROVE; read `mergeable_state` / GraphQL `reviewDecision` and attempt a merge. Repeat with the reviewer App granted `contents: write`. Record which variant satisfies the rule.

### Machine accounts under the GitHub Terms (§16 item 1, fallback)

**Answer:** Only needed if App approvals do not count. The Terms allow one person no more than one free machine account in addition to their free personal account. The owner is responsible for the machine account's actions. Two reviewer roles (`review-correctness`, `review-security`) would need two machine users, which is more than one free machine account per person; the second needs a paid account, a second responsible human, or an organisation-owned arrangement.

**Evidence:** "You may maintain no more than one free machine account in addition to your free Personal Account." https://docs.github.com/en/site-policy/github-terms/github-terms-of-service (section "Account Requirements").

**Confidence:** documented.

**Consequence for spec:** Only if `app-approval-counts` fails: D6 fallback must say one free machine user per operator at most, so V1 would use one machine reviewer for the native approval and keep the second reviewer role enforced only by the DDF gate (§6.6), or require a paid account.

**M4 probe:** none (legal text, not behaviour). Re-read the Terms before M4 in case they changed.

### Installation token narrowing (§16 item 2)

**Answer:** Supported. `POST /app/installations/{installation_id}/access_tokens` (authenticated with the App JWT) accepts `repositories` (names) or `repository_ids` (up to 500 combined) and a `permissions` object. Without `permissions` the token gets every permission the App has. A token cannot get repositories the installation was not granted, nor permissions the App was not granted. Tokens expire one hour after creation; an expired token returns 401. `permissions.workflows` exists as a separate permission (only value `write`). The response code for requesting a permission the installation lacks is not documented (listed codes: 201, 401, 403, 404, 422). This applies identically to all three Apps; it is the same endpoint.

**Evidence:** https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app ("Installation tokens expire one hour from the time you create them.").

**Confidence:** documented.

**Consequence for spec:** None. §8.2 "narrowed to one repository and the permissions that operation needs (lifetime ≤ 1 h)" matches the API. The token broker should treat any non-201 on a narrowing request as a hard failure (never retry without `permissions`), since omitting `permissions` silently widens the token.

**M4 probe:** `token-narrowing` — for each App mint a token with one `repository_ids` entry and a strict permission subset; check `GET /installation/repositories` lists only that repository, a write outside the subset returns 403, and a request for a permission the App lacks fails (record status and message).

### Sync when the base changed workflow files (§16 item 3)

**Answer:** `update-branch` is rejected. A public third-party report shows `PUT /repos/{owner}/{repo}/pulls/{pull_number}/update-branch` with an App installation token lacking `workflows` returning HTTP 403 "refusing to allow a GitHub App to create or update workflow `<path>` without `workflows` permission" whenever the base contained new or changed files under `.github/workflows/`. The official endpoint docs are silent on this (they only require write access to the head repository's contents). A pushed base-merge commit is very likely rejected the same way: the same error is reported for App git pushes that bring workflow-file changes, and a merge commit with the base as second parent changes workflow files relative to the PR head. Not observed for the push path.

**Evidence:**
- Endpoint docs, no mention of `workflows`: https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request-branch
- 403 on `update-branch` from an App without `workflows` when the base changed workflow files: https://github.com/petry-projects/.github/pull/141
- Same error on App git pushes: https://github.com/orgs/community/discussions/35410

**Confidence:** unverified (third-party observation for `update-branch`; inference for the pushed merge).

**Consequence for spec:** Forced change likely. §5.2 "Sync with base" (daemon merges the base into the branch) will fail whenever the base gained workflow-file changes, because §8.2 deliberately withholds `workflows`. Keep withholding `workflows` (it is the defence that stops agent changes to CI), and add a defined outcome: a sync refused with this 403 sends the change to `needs-owner` with the reason "base changed workflow files; update the branch manually", without consuming a sync batch. A human "Update branch" click produces a commit not created by the daemon, so the §6.6 rule 4 ancestor exception does not apply and the change goes through full re-review; the spec should state that explicitly.

**M4 probe:** `sync-with-workflow-change` — on a test repository: open a PR from the `worker` App; push a workflow-file change to the base as a human; then (a) call `update-branch` with a `worker` token without `workflows`, (b) push a daemon-created merge commit with the same token over HTTPS. Record status codes and messages for both, and confirm a sync with no workflow changes in the base still succeeds.

## `node:sqlite` (§16 item 6)

**Answer:** Usable without warnings on Node 24.21.0. `require('node:sqlite')` and a file-backed write/read roundtrip (WAL mode, prepared statements, close and reopen) both exit 0 with empty stderr: no `ExperimentalWarning`. Warning output was confirmed working in the same environment (a manual `process.emitWarning` printed). The bundled SQLite reports version 3.54.1. Documented stability is 1.2 (release candidate), not 2 (stable); the module was promoted to release candidate in v24.15.0, and before that dropped the `--experimental-sqlite` flag in v22.13.0/v23.4.0.

**Evidence:**
- Local run, Node v24.21.0, no `NODE_OPTIONS` / `NODE_NO_WARNINGS` set: `node -e "require('node:sqlite')"` → exit 0, stderr empty; roundtrip script → stdout `roundtrip {"id":1,"body":"{\"k\":\"v\"}"} sqlite 3.54.1`, stderr empty.
- Stability and history: https://nodejs.org/docs/latest-v24.x/api/sqlite.html ("Stability: 1.2 - Release candidate"; v24.15.0 "SQLite is now a release candidate").

**Confidence:** verified (warning behaviour); documented (stability index).

**Consequence for spec:** None. §4.1/§4.4 (`node:sqlite`, no dependency) stand. Pin Node at or above 24.15.0 (release candidate, no warning); keep store access behind the `store` module so a release-candidate API change touches one place, and run the store tests on every Node bump.

**M4 probe:** none required; M2 store tests on the pinned Node cover it.

## colima under a service user (§16 item 5)

Probe setup (throwaway, outside the repository; one run on 2026-11-04): Apple Silicon macOS host, colima 0.10.3, limactl 2.2.1, Docker CLI 29.9.3, VM image Ubuntu 24.04 (kernel 6.8, cgroup v2, `iptables` 1.8.10 nf_tables backend, Docker Engine 29.5.2 with the iptables firewall backend). A test HTTP listener ran as the owner on the host's loopback interface (`<loopback>:<port>`). The probe script ran as `ddf` (`sudo -u ddf -H bash ~ddf/m0/02-probe.sh`); the VM was started only by the LaunchDaemon. Addresses below are placeholders: `<vm-net>` is the VM's user-mode network, `<gateway>` the lima gateway (`host.lima.internal`), `<vm-ip>` the VM's own address, `<bridge-gw>` the Docker bridge gateway.

### Service user and LaunchDaemon start-up

**Answer:** Works. A hidden, standard (non-admin) user `ddf` with home mode 700 runs colima from a system LaunchDaemon (`UserName=ddf`) with `vz` and `virtiofs`; the VM, `limactl hostagent` and `limactl usernet` all run as `ddf`; `colima status` and `docker info` as `ddf` succeed, using `~ddf/.colima/default/docker.sock`. The shared Homebrew binaries (`colima`, `limactl`, `docker`, the lima guest agent) are usable by `ddf` without a per-user install. First start (image download included) took about 2.5 min. Two setup pitfalls were hit and fixed: the owner shell's restrictive umask, inherited through `sudo`, made `~ddf/.colima` unwritable (`mkdir … permission denied`) — the setup script must set `umask 022` and fix ownership of an existing `~ddf/.colima`; and every `sudo -u ddf` command must `cd ~ddf` first, because `ddf` cannot read the caller's working directory.

**Evidence:** setup log: `sysadminctl -addUser` (uid assigned, "Home directory is assigned (not created!)" → `createhomedir -c` needed), `dscl` `IsHidden 1` on the `ddf` record, admin membership check negative, `colima start --foreground` up after the image download. Probe log section A: `ps` shows `colima start --foreground …`, `limactl usernet`, `limactl hostagent` and the ssh mux owned by `ddf`; `launchctl print system/com.ddf.colima-probe` → `state = running`, `username = ddf`, `properties = keepalive | runatload`.

**Confidence:** verified (start at load). Unverified: start after a host reboot (not run), start while no user is logged in.

**Consequence for spec:** None for §8.1. The M5 setup must include `createhomedir`, `IsHidden`, `umask 022`, and `cd ~ddf` in every `sudo -u ddf` step.

**M5 probe:** `colima-boot` — reboot the host, do not log in, and check from SSH or the next login that `sudo -u ddf colima status` is running and that the firewall probe passes.

### Host reachability without a firewall

**Answer:** Without VM rules a container reaches services bound to the host's loopback. lima's user-mode network maps `<gateway>` (`host.lima.internal`) to the host's loopback interface, and Docker writes `host.lima.internal` and Docker's own host alias (both → `<gateway>`) into every container's `/etc/hosts`. Containers on the default bridge and on a user-defined network both got HTTP 200 from the owner's loopback-only listener, by name and by IP. A container could also reach the VM itself (its sshd on `<bridge-gw>:22` answered). This means every loopback service of every macOS user is exposed to containers unless the VM firewall is in place, so §14.1 probe 6 is a real boundary, not a formality.

**Evidence:** probe log phase B: all four host checks `rc=0 http=200`; VM resolver `<vm-ip>`; `getent ahostsv4 host.lima.internal` → `<gateway>`; container `/etc/hosts` lists both aliases.

**Confidence:** verified.

**Consequence for spec:** None (the §8.4 design already assumes this). Also covers the §16 item 5 "coexistence" question for network exposure: other users' loopback services are reachable from containers without the rules.

### VM firewall rules

**Answer:** Applying `firewall.sh` as root inside the VM blocks the host and the VM from containers while leaving the internet open. Content: create chain `DDF-HOSTBLOCK`, hooked from `DOCKER-USER` for `-i docker0` and `-i br-+` (default bridge and all user-defined networks): RETURN for DNS (udp/tcp 53) to the VM's resolver, then DROP to the VM's user-mode network `<vm-net>`, to the default-route gateway and to the resolved `host.lima.internal`. Create chain `DDF-VMBLOCK`, hooked from `INPUT` for the same interfaces: RETURN for ESTABLISHED/RELATED and for port 53, DROP everything else (blocks the VM's sshd and any other VM service). Addresses are discovered at run time (`ip -4 route`, `ip -4 addr`, `getent`, `resolv.conf`), so nothing is hard-coded. The script is idempotent (`-N … || true`, `-F` of its own chains, `-C … || -I`). After applying it: host by name and IP on the bridge, on a user network, with `--add-host`, and via Docker's host alias → timeout (curl rc 28); `<bridge-gw>:22` → timeout; HTTPS to the model API from both networks → connected; DNS still resolves. The VM itself (not a container) can still reach the host, which is expected and needed by colima.

**Evidence:** probe log phase C: rule listing (`-A FORWARD -j DOCKER-USER` first in FORWARD, `DOCKER-USER` → `DDF-HOSTBLOCK` for `docker0` and `br-+`, `INPUT` → `DDF-VMBLOCK`), every host/VM check `rc=28 http=000`, internet `rc=0`.

**Confidence:** verified (manual application on a running VM).

**Consequence for spec:** None for the design of §8.4; the rules above are the content of the "VM firewall" component in M3. Known gap, accepted by §8.4 as written: IPv6 is not filtered (the VM had no global IPv6 address in this run).

### Rule persistence across VM restarts

**Answer:** Rules do not persist. After `colima stop` and a new `colima start` (and after an explicit `colima stop && colima start`), `DDF-HOSTBLOCK` and `DDF-VMBLOCK` do not exist, `DOCKER-USER` is empty, and containers reach the host again. The colima `provision` entries with modes `after-boot` and `ready` (documented in the colima 0.10.3 config template: "after VM boot, before container runtimes start" and "after VM and container runtimes are ready") are executed on every `colima start` and survive in `colima.yaml` (both entries intact after the run), but they failed in this run: colima runs them as the VM's login user, not as root. Each run printed the script's first line and then `iptables … Could not fetch rule set generation id: Permission denied (you must be root)`, and colima logged `level=warning msg="error running after-boot provision script(s)"` / `"error running ready provision script(s)"` — a warning only: `colima start` still exited 0 and reported `done`. So the failure was the script assuming root, not the hook mechanism, and a failed hook is silent to anything that only checks `colima status`.

**Evidence:** probe log phases D, F, G (rule listings and `rc=0 http=200` from containers to the host after each restart; provision output with the permission error and the two warnings, twice); `colima.yaml` after the run (both entries present and byte-identical to `firewall.sh`).

**Confidence:** verified (rules lost on restart; provision hooks run on every start, as the VM user, and their failure is only a warning). Unverified: that the hooks apply the rules once the script elevates with `sudo -n` (the corrected script and a rerun probe exist in the throwaway notes); whether Docker keeps rules in a pre-created `DOCKER-USER` chain when the `after-boot` run precedes `dockerd` (the `ready` run covers it either way).

**Consequence for spec:** §8.4 as designed is confirmed: the daemon itself must re-apply the rules after every VM start and probe them before admitting any run. Provision hooks are usable only as an additional layer (they narrow the window between VM start and the daemon's re-apply) and must never be the guarantee, because their failure does not fail `colima start`. Add to §8.4: "Before any container start, the daemon checks that `DDF-HOSTBLOCK` and `DDF-VMBLOCK` exist and are hooked, and runs the host-reachability probe; if either fails, it re-applies the rules once and re-probes; still failing → container runtime unavailable (§9)."

**M3 probe:** `vm-firewall-reapply` — `colima stop && colima start`, then without manual action check that the daemon's pre-run check detects missing rules, re-applies them, and that a container gets a timeout to a host loopback listener and a connection to the internet.

### Restart supervision by launchd

**Answer:** launchd `KeepAlive` does not restart the VM. `colima start --foreground` starts the VM and then only waits for a signal; when the VM is stopped by `colima stop` (twice in this run, each time waiting 300 s), the foreground process keeps running (same PID throughout the 18-minute run, `launchctl print` → `runs = 1`, `last exit code = (never exited)`), writes nothing to its log, and launchd has nothing to restart. `ThrottleInterval` (shown as `minimum runtime = 30`) is irrelevant. `limactl hostagent` and `usernet` are reparented to PID 1, so the foreground process does not watch them either. A later `colima start` by `ddf` (outside launchd) started the VM normally while the stale foreground process stayed alive; the two did not conflict. `launchctl print` showed `exit timeout = 60` although the plist sets `ExitTimeOut` 120.

**Evidence:** probe log phases D, F and G: `ps` and `launchctl print` after each stop; daemon stderr unchanged since the first start.

**Confidence:** verified (no restart after `colima stop`). Unverified: whether launchd respawns the job when the foreground process itself exits or is killed, and whether SIGTERM to it stops the VM (rerun phase K); behaviour after a VM crash.

**Consequence for spec:** §8.1/§9: launchd supervises `ddfd`, not the VM. `ddfd` owns colima health: before each run and on every tick with runs pending it checks `colima status` and `docker info`; if the runtime is down it runs `colima start` as `ddf` (no root needed; observed to work) with a bounded number of attempts, then re-applies and probes the VM rules. Only when that fails does §9 "container runtime unavailable → global pause, notify" apply; the pause is lifted automatically once a later health check, rule re-apply and probe pass (owner `/resume` not required, but notified). The launchd colima job stays only as the boot-time starter.

**M3 probe:** `runtime-recovery` — stop the VM while the daemon is idle; the next tick restarts it, re-applies the rules, probes, and admits a run; with colima made unstartable, the daemon enters global pause and notifies.

### Container limits

**Answer:** Enforced. `--memory 3g --memory-swap 3g --cpus 2 --pids-limit 256` produces `memory.max` 3 GiB, `cpu.max` `200000 100000` and `pids.max` 256 in the container's cgroup (v2); four busy processes reached 200 % CPU in `docker stats` (capped at 2 CPUs); a process allocating up to 4.5 GiB was killed at about 2.8 GiB with `OOMKilled=true`, exit code 137, and a memcg OOM in the VM kernel log (not a VM-wide OOM). The VM (8 GiB, no swap) stayed up and kept 7 GiB free after the kill. The host's memory-free percentage was the same before and after (44 %).

**Evidence:** probe log phase limits: `docker inspect` HostConfig values, cgroup files, `docker stats`, `docker logs`, `State.OOMKilled`, `dmesg`.

**Confidence:** verified (limits). Unverified: effect on the owner's interactive work (not measured beyond host memory statistics; the host was under unrelated load) and coexistence with a second colima/lima instance of another macOS user (the owner's own colima was stopped for the probe; lima logged a harmless failure to forward guest port 53 when the port was busy).

**Consequence for spec:** None. The §8.4 defaults (3 GB, 2 CPU, pids limit) are enforceable as written; the sandbox adapter maps an OOM kill (exit 137 with `OOMKilled`) to a distinct run failure reason.

### What §8.4 and §9 should say (forced changes)

- §8.4: keep "re-applied by the daemon on every VM start or recreation"; add that the daemon also verifies rule presence and runs the host-reachability probe **before every container start** (not only at daemon start), because a VM restart by anyone (owner, `colima`, a crash) silently drops the rules and a failed provision hook does not fail `colima start`. colima `provision` hooks are an optional extra layer, never the guarantee.
- §9: "container runtime unavailable → global pause, notify" applies after the daemon's own restart attempt (`colima start` as `ddf`, bounded attempts, then rule re-apply and probe) fails; a missing or unverifiable VM firewall counts as runtime unavailable. The "host sleep → launchd restarts the daemon" row stays, but launchd must not be relied on to restart colima.
